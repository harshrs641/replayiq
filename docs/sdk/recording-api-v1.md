# ReplayIQ Recording API v1

The contract every ReplayIQ SDK implements: web, Flutter, iOS (Swift), Android
(Kotlin) and React Native. An SDK that follows this document needs no server
changes. Version: **1.0** (2026-11).

## Overview

```
SDK                                           ReplayIQ
 │  POST /api/v1/sessions              ───▶  create the session (idempotent)
 │  POST /api/v1/events   (every ~5 s) ───▶  append a batch of events
 │  POST /api/v1/sessions/{id}/end     ───▶  close it; starts the AI analysis
```

All requests are JSON over HTTPS to the customer's ingest host (SaaS:
`https://ingest.replayiq.<domain>`, self-hosted: their own host).

## Authentication

Every request carries the project's **ingest key**:

```
Authorization: Bearer <ingest key>
```

Ingest keys are write-only: they can create sessions and send events, never
read anything, so they are safe to ship inside apps and web pages.

> **Interim (until ingest keys exist):** the key is the project id. The
> server takes the project from `project_id` in the body, else from the key.
> SDKs must send the header from day one so no SDK release is needed when
> keys are enforced.

## Compression

Request bodies may be gzipped (`Content-Encoding: gzip`). Mobile SDKs
**should** always gzip: screenshot batches shrink well. Limits apply to the
decompressed body.

## Limits

| | |
|---|---|
| Body (decompressed) | 5 MB per request. Split larger batches. |
| One event | 2 MB (a screenshot must fit). |
| Batch cadence | Flush every 5 s, at 50 events, and when the app/tab goes to the background. |

## 1. Start a session: `POST /api/v1/sessions`

```json
{
  "session_id": "8f0c2c1e-3c4b-4a8e-9d51-0f6f2f1c9a10",
  "project_id": "acme-web",
  "user_id": "user_123",
  "url": "https://shop.example.com/checkout",
  "user_agent": "Mozilla/5.0 ...",
  "screen_width": 1440,
  "screen_height": 900,
  "sdk_version": "replayiq-flutter/1.0.0",
  "started_at": "2026-11-19T10:15:02.120Z",
  "metadata": {
    "platform": "flutter",
    "os": "ios",
    "os_version": "26.1",
    "app_version": "4.2.0 (318)",
    "device": "iPhone17,3"
  }
}
```

- `session_id`: generated by the SDK, a UUID v4. A web session lives for the
  browser tab (sessionStorage); a mobile session ends after 30 min in the
  background or on an explicit reset.
- `url`: web: the page URL. Mobile: `app://<bundle id>/<first screen>`.
- Calling it again for the same `session_id` is a no-op, so SDKs may send it
  on every app start or page load.
- `metadata.platform`: one of `web`, `flutter`, `ios`, `android`,
  `react-native`. Add any other string-valued keys you like.

Response: `201 {"session_id": "..."}`.

## 2. Send events: `POST /api/v1/events`

```json
{
  "session_id": "8f0c2c1e-...",
  "project_id": "acme-web",
  "batch_id": "8f0c2c1e-...-000017",
  "platform": "flutter",
  "sdk": "replayiq-flutter/1.0.0",
  "device_masked": true,
  "flushed_at": "2026-11-19T10:15:07.300Z",
  "events": [ ... ]
}
```

- `batch_id`: unique per batch, and **the same on every retry of that
  batch** (e.g. `<session_id>-<sequence>`). The server stores a batch under
  its id, so a retried batch replaces itself instead of duplicating events.
- `device_masked`: `true` when the SDK has already masked sensitive content
  on the device. Required for screenshot recording (mobile): the server
  cannot mask pixels.
- `events`: ordered by `timestamp` (unix ms). Every event has `type` and
  `timestamp`.
- `custom_events` (optional): the app's own named events,
  `[{"name": "checkout_started", "properties": {...}, "timestamp": ...}]`.

Response: `202 {"status": "accepted"}`.

### Event types

`type` follows rrweb's numbering: `2` FullSnapshot, `3` IncrementalSnapshot,
`4` Meta, `5` Custom. SDK events are Custom (`type: 5`) with a `subtype`.

#### Screen recording: web

The web SDK sends rrweb's own events (types 2, 3 and 4) unchanged, with a
Meta + FullSnapshot pair ("keyframe") at least every 30 s of activity.

#### Screen recording: mobile (screenshots)

Mobile SDKs send screenshots and touches; the server turns them into
replayable events.

**`screen`**: one frame.

```json
{ "type": 5, "subtype": "screen", "timestamp": 1794995702120,
  "width": 393, "height": 852,
  "image": "data:image/jpeg;base64,/9j/4AAQ...",
  "keyframe": true }
```

- `width`/`height`: the screen in logical points (not pixels). The image may
  be any resolution with that aspect ratio; 1x–2x JPEG at quality ~0.6 is a
  good trade-off.
- `keyframe: true` on the first frame of the session, on every orientation
  or size change, and at least every 30 s. Playback and seeking start from
  keyframes. Other frames have `keyframe: false`.
- Send a frame only when the screen changed; at most 2 per second.
- **Masking happens before encoding.** Text inputs, password fields and
  anything the app marks sensitive are painted over on the device.

**`touch`**: a finger down, move or up, in the same logical points.

```json
{ "type": 5, "subtype": "touch", "timestamp": 1794995703050,
  "x": 196, "y": 610, "phase": "down" }
```

`phase`: `down`, `move` (send at most every 50 ms) or `up`.

#### Behaviour, app events and errors: every platform

These drive the dashboard's Behaviour / Console / Network tabs, the timeline
markers and the AI analysis. Fields not listed are ignored.

| `subtype` | Fields | When |
|---|---|---|
| `navigate` | `url`, `message` | Page or screen change. Mobile: `app://<bundle id>/<route>`. |
| `click` | `selector` | A tap or click. `selector` names the element: web `button#pay.primary`; mobile `button:"Pay now"` (role, then the visible label). |
| `rage_click` | `selector`, `x`, `y` | 3+ taps within 700 ms and 48 pt of each other. |
| `input` | `selector` | A text field was edited (never the value). |
| `console` | `level` (`log`/`warn`/`error`), `message`, `stack` | Log lines. |
| `js_error` | `message`, `filename`, `lineno`, `colno`, `stack` | Uncaught errors / crashes (the name is historical: all platforms use it). |
| `network` | `method`, `url`, `status`, `duration` (ms), `error` | One per HTTP request. `status: 0` plus `error` when no response arrived. |

Text in these events (`message`, `url`, `selector`, `stack`, `error`) is
redacted for PII patterns on the server, but SDKs should not send request
bodies, headers or field values at all.

## 3. End a session: `POST /api/v1/sessions/{session_id}/end`

```json
{ "ended_at": "2026-11-19T10:21:40.000Z", "duration_ms": 398000 }
```

Send it when the session ends (web: page unload of the last tab; mobile:
after 30 min in the background, or on logout/reset). It starts the AI
analysis. Sessions that never send it are still kept; they just aren't
analysed automatically.

## Errors and retries

| Status | Meaning | SDK should |
|---|---|---|
| 2xx | Accepted | Drop the batch. |
| 400 | Malformed | Drop the batch (retrying won't help) and log once. |
| 401 / 403 | Bad or revoked key | Stop recording for this app run. |
| 413 | Too large | Split the batch and resend. |
| 429 | Rate limited | Retry after `Retry-After` seconds. |
| 5xx / network error | Temporary | Retry with backoff (1 s, 2 s, 4 s ... max 60 s), same `batch_id`. Keep at most ~5 MB or 1000 events buffered, dropping the oldest. |

Mobile SDKs should persist unsent batches to disk so they survive an app
kill, and send them on the next launch.

## SDK behaviour checklist

- Sampling: `sampleRate` 0–1, decided once per session, before any
  recording starts. Unsampled sessions send nothing.
- Consent: `optOut()` / `optIn()`; while opted out nothing is recorded or
  sent.
- `identify(userId, traits)` sets `user_id` (and metadata) for the session.
- Never block or crash the host app: every SDK failure is caught and logged
  in debug builds only.
- Performance budget: capture work off the main thread where the platform
  allows; under 2% CPU on average, and pause recording while backgrounded.
- Versioning: SDKs send `sdk` as `<name>/<semver>`. The API is versioned by
  path (`/api/v1`); fields are only ever added within v1.
